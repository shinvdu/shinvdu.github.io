API Server

kube-apiserver is one of the most important core components of Kubernetes. Its main responsibilities are:

  • Providing the REST API for cluster management, including authentication, authorization, data validation, and cluster state changes
  • Acting as the hub for data exchange and communication between other modules (other modules query or modify data through the API Server; only the API Server directly operates on etcd)

REST API

kube-apiserver can serve both HTTPS (listening on port 6443 by default) and HTTP (listening on 127.0.0.1:8080 by default). The HTTP API is insecure and performs no authentication or authorization; do not enable it in production. Both endpoints expose the same REST API format. See the Kubernetes API Reference for the call format of every API.

Local port

  • Receives HTTP requests
  • Defaults to 8080; change it with the API Server’s --insecure-port startup flag
  • Defaults to the localhost IP; change it with the --insecure-bind-address startup flag
  • Unauthenticated and unauthorized HTTP requests reach the API Server through this port

Secure port

  • Defaults to 6443; change it with the --secure-port startup flag
  • The default IP is a non-local host network address; set it with the --bind-address startup flag
  • Receives HTTPS requests
  • Used for authentication based on token files, client certificates, and HTTP Basic auth
  • Used for policy-based authorization
  • HTTPS access control is not enabled by default

Node-related endpoints

The REST path for Node-related endpoints is /api/v1/proxy/nodes/{name}, where {name} is the node name or IP address.

1
2
3

/api/v1/proxy/nodes/{name}/pods/    # List information about all Pods on the specified node
/api/v1/proxy/nodes/{name}/stats/   # List statistics about physical resources on the specified node
/api/v1/prxoy/nodes/{name}/spec/    # List summary information about the specified node

The Pod information obtained here comes from the Node rather than the etcd database, so the two may differ in time. If you start the kubelet process with --enable-debugging-handles=true, the Kubernetes Proxy API also exposes:

/api/v1/proxy/nodes/{name}/portForward   # Forward ports for Pods on the node
/api/v1/proxy/nodes/{name}/logs     # List various logs for the node
/api/v1/proxy/nodes/{name}/metrics  # List metrics related to the node
/api/v1/proxy/nodes/{name}/runningpods  # List running Pods on the node

1. Generate the CA key and certificate

1

$ openssl req -x509 -sha256 -newkey rsa:4096 -keyout ca.key -out ca.crt -days 356 -nodes -subj '/CN=Fern Cert Authority'

2. Generate the server key and certificate, and sign them with the CA certificate

1
2

$ openssl req -new -newkey rsa:4096 -keyout server.key -out server.csr -nodes -subj '/CN=meow.com'
$ openssl x509 -req -sha256 -days 365 -in server.csr -CA ca.crt -CAkey ca.key -set_serial 01 -out server.crt

3. Generate the client key and certificate, and sign them with the CA certificate

1
2
3

$ openssl req -new -newkey rsa:4096 -keyout client.key -out client.csr -nodes -subj '/CN=Tiabao'

$ openssl x509 -req -sha256 -days 365 -in client.csr -CA /etc/kubernetes/pki/ca.crt -CAkey /etc/kubernetes/pki/ca.key -set_serial 02 -out client.crt

For a typical application, the user provides a username and password, the server checks the database to see whether they exist and are valid, and authentication succeeds or fails accordingly.

How does Kubernetes do it?

Although ordinary users cannot be created through API calls, Kubernetes cleverly authenticates users via certificates. In other words, any user who can present a valid certificate is authenticated by Kubernetes.

After authentication, Kubernetes treats the certificate’s CN as the username (for example, /CN=joker means the username is Joker) and the Organization as the user’s group. A Role bound to that username and group then determines the user’s permissions.

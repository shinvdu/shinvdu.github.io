关键事实

  • mcp-chrome-bridge 是谁启动的？ — Chrome 启动的。Chrome 根据 Native Messaging Host 配置（/etc/opt/chrome/native-messaging-hosts/com.chromemcp.nativehost.json）在启动时自动把 mcp-chrome-bridge 作为子进程拉起来
  • 是共用还是每个 Claude 会话一个？ — 共用。只有一个守护进程，从 7 月 19 号运行至今，所有 Claude 会话都连到同一个 127.0.0.1:12306
  • Chrome 和 mcp-chrome-bridge 是两个独立进程吗？ — 是的，父子关系。Chrome 是父进程，mcp-chrome-bridge 是子进程

Native Messaging 协议详解

这是 Chrome 扩展与本地程序通信的标准机制，不是网络端口，而是管道。

注册方式

Native Messaging Host 配置文件告诉 Chrome 如何启动本地程序：

/etc/opt/chrome/native-messaging-hosts/com.chromemcp.nativehost.json

1
2
3
4
5
6
7
8

{
  "name": "com.chromemcp.nativehost",
  "path": "/usr/local/.../mcp-chrome-bridge/dist/run_host.sh",
  "type": "stdio",
  "allowed_origins": [
    "chrome-extension://hbdgbgagpkpjffpklnamcljpakneikee/"
  ]
}
  • type: "stdio" — 通过 stdin/stdout 通信
  • path — Chrome 要启动的程序路径
  • allowed_origins — 只允许指定的扩展连接

消息格式

┌──────────┬─────────────────────────────┐
│  4 字节   │          JSON 数据           │
│  (长度)   │    (UTF-8 编码的 JSON 字符串) │
│ 小端整数  │                              │
├──────────┼─────────────────────────────┤
│  0x1A    │ {"type":"request",...}       │

  1. 先写入 4 字节小端整数，表示后面 JSON 的长度
  2. 然后写入 JSON 字符串
  3. 接收方先读 4 字节拿到长度，再读对应字节数的 JSON

Chrome 扩展侧 API

Chrome 扩展通过 chrome.runtime.connectNative('com.chromemcp.nativehost') 建立连接，得到一个 Port 对象，通过 port.postMessage() 和 port.onMessage 通信。

步骤 1: Claude 调用 chrome-control 的 get_windows_and_tabs 工具
         ↓
步骤 2: mcp-chrome-bridge 的 MCP Server (stdio CLI) 收到调用
         ↓  HTTP POST (127.0.0.1:12306/mcp)
步骤 3: mcp-chrome-bridge 守护进程 (端口 12306) 收到请求
         ↓  内部转发到 Native Messaging Host 模块
步骤 4: Native Messaging Host 将请求序列化为 JSON
         ↓  按 Native Messaging 格式写入 stdout
步骤 5: Chrome 扩展的 stdin 接收到消息
         ↓  扩展解析 JSON, 识别为 get_windows_and_tabs 命令
步骤 6: 扩展通过 CDP 向 Chrome 查询窗口/标签页信息
         ↓  CDP 请求: Target.getTargets, Browser.getWindowForTarget 等
步骤 7: Chrome 返回 CDP 响应
         ↓  扩展收到窗口/标签页数据
步骤 8: 扩展将结果序列化为 JSON
         ↓  按 Native Messaging 格式写入 stdout
步骤 9: mcp-chrome-bridge 的 stdin 接收到响应
         ↓  解析 JSON, 准备 HTTP 响应
步骤 10: 守护进程返回 HTTP 200 + JSON 数据
          ↓
步骤 11: MCP Server 收到响应, 返回给 Claude
          ↓
步骤 12: Claude 拿到窗口/标签页列表

工作原理

层级协议组件
Claude → 桥HTTP (端口 12306)MCP Server ↔ mcp-chrome-bridge 守护进程
桥 → Chrome扩展Native Messaging (stdin/stdout)守护进程 ↔ Chrome Extension
扩展 → 页面CDP (Chrome DevTools Protocol)扩展内部通过 CDP 操控浏览器标签页

关键点

  • 不需要 --remote-debugging-port 启动参数
  • 不需要 socket/pipe 文件
  • Native Messaging 走的是 stdin/stdout 管道，消息格式是 [4字节长度][JSON]
  • Chrome 扩展内部使用 CDP 访问标签页，和 DevTools 开发者工具用的是同一套协议

不能做什么

  • 访问未打开的网页
  • 读取浏览历史、书签、密码
  • 安装扩展或修改浏览器设置
  • 获取已关闭标签页的内容

局限性

CDP 被占用时 JavaScript 无法执行

chrome-mcp-server 扩展本身占用了 CDP 连接。当 CDP 被占用时，chrome_javascript 会 fallback 到 chrome.scripting.executeScript（isolated world），但实际测试中 fallback 也无法返回结果。这意味着在部分场景下无法通过 JavaScript 批量提取数据。

无结构化数据提取工具

缺少的能力影响
内置 DOM 查询 / CSS 选择器数据提取列表页（如种子列表）的数据只能拿到纯文本，需要外部 Python 脚本二次解析
无 page.$$eval() 等价操作Playwright/Puppeteer 那种直接在页面上执行选择器并返回结构化 JSON 的能力不存在
返回值为非结构化文本chrome_get_web_content 和 chrome_read_page 都返回纯文本，表格类数据丢失行列结构

适用场景对比

场景chrome-controlPlaywright/Puppeteer
点击、填表、导航✅ 方便✅ 方便
读取页面可见文本✅ 可用✅ 可用
批量提取列表数据❌ 需外部脚本解析✅ page.$$eval() 一行搞定
操作已有登录态页面✅ 天然支持❌ 需自己处理 Cookie

会话复用

Chrome 中的登录态（Cookie/Session）自动继承。在某个标签页已登录的站点（如 M-Team），直接在该标签页上下文中操作即携带登录态。

常见问题

Chrome Control MCP 服务器未连接

1

Chrome 控制 MCP 服务器当前未连接

可能原因：

  • ~/.claude.json 中的配置被修改或删除
  • mcp-chrome-bridge 守护进程未运行（端口 12306 无监听）
  • Chrome 扩展被禁用或卸载
  • Chrome 重启后 mcp-chrome-bridge 子进程未正确启动

解决：

  1. 确认 ~/.claude.json 中 chrome-control 配置存在
  2. 检查端口 12306 是否在监听：ss -tlnp | grep 12306
  3. 检查 Chrome 扩展 hbdgbgagpkpjffpklnamcljpakneikee 是否启用
  4. 重启 Chrome（会连带重启 mcp-chrome-bridge 子进程）
  5. 重启 Claude Code

工具调用报 “Failed to connect to MCP server” / “Already connected to a transport”

症状：chrome-control 工具调用全部失败，报 Failed to connect to MCP server。claude mcp list 却显示 ✔ Connected。

根因（2026-08-12 定位）：mcp-chrome-bridge 1.0.31 的守护进程（dist/server/index.js）在 /mcp 和 /sse 路由里用单例 MCP Server（getMcpServer()，见 dist/mcp/mcp-server.js）连接每个新 transport。而 MCP SDK 的 Protocol.connect() 只允许一个 transport（protocol.js 抛 “Already connected to a transport”）。一旦某个客户端异常断开、transport 未触发 onclose，单例就永久卡死，之后所有新连接全部被拒。守护进程 stderr 日志会堆满 ERR_HTTP_HEADERS_SENT（旧日志涨到 200MB+）。

修复（已打补丁到 dist/）：

  1. dist/mcp/mcp-server.js：新增 createMcpServer() 工厂，每次返回独立注册了工具的 Server 实例
  2. dist/server/index.js：/mcp 和 /sse 路由改用 createMcpServer()（替换 getMcpServer()），每个连接独立 Server
  3. dist/server/index.js GET /mcp 路由：删除手动预写 SSE 头（setHeader/flushHeaders），改为 reply.hijack() 后完全交给 SDK transport 写头，消除 ERR_HTTP_HEADERS_SENT

验证：端到端单连接 ✓，3 个并发客户端同时连接全部成功 ✓，日志 0 错误 ✓。

注意：补丁是直接改的 dist/ 编译产物，升级 npm 包会被覆盖。升级后需重新打补丁。备份在修复时已删，改前建议先 cp 备份。

恢复步骤：

  1. 杀掉损坏的守护进程（Chrome 扩展会自动重连拉起新的）：
    1
2

    ss -tlnp | grep 12306   # 找到 pid
kill <pid>
  2. 若某会话仍连不上（其 stdio 客户端缓存了旧连接），重启该 Claude 会话或 /mcp 重连。

Chrome 不响应操作

操作卡住没有返回时，可能原因：

  • 页面弹出了对话框（alert/confirm/prompt）
  • 页面正在加载中
  • 页面有未关闭的模态框

解决：用 chrome_handle_dialog 处理弹窗，或手动关闭后重试。

元素找不到

chrome_read_page 返回的内容中没有目标元素：

  • 元素在 viewport 之外，用 scroll_to 滚动后再试
  • 元素在 iframe 中，需要指定 frameId
  • 页面是动态加载的（SPA），等待数据加载后再读取

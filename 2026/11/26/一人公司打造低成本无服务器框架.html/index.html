题记

这是「一人技术公司」系列的第三篇。现在 OPC (One Person Company) 的概念很火，我也尝个鲜，看看真要严肃地使用周末来做点一家技术公司才能做起来得事情，到底能做成啥样。这并不意味着我要全职创业，我认为我自己是个一直在路上的创业者，朝九晚五从来不是我的束缚。我想通过这个过程，了解 AI 的边界，以及我自己的边界。

整个系列将记录我从零搭建一套完整技术体系的全过程 —— 从基础设施，到网络与运行时，到核心框架，再到应用服务。这不是一篇教程，而是一份带有思考过程的实战手记。

前两篇我们分别聊了用 IaC 搭建 AWS 访问控制和安全架构，以及服务架构的取舍。地基打好了，接下来得回答一个灵魂拷问：就你一个人，后端服务到底怎么跑？

答案几乎是唯一的：无服务器（Serverless）。

但问题是，市面上的无服务器框架过分追求通用，塞满了你用不上的抽象和无意义的灵活性。于是我干了一件看起来很离谱的事：自己用 Rust 撸了一个完整的无服务器框架，从运行时到 CLI 工具，从认证系统到基础设施模板，全家桶一步到位。

这篇文章，我把这一路上踩过的坑、做过的取舍、悟到的道理，掰开了揉碎了讲给大家听。

一、为什么一人公司必须拥抱无服务器

设身处地想想你的处境：你一个人，身兼产品经理、架构师、前端、后端、运维、客服六职。没有值班轮换表，凌晨三点服务器炸了只能自己爬起来救火。没有运维团队帮你打补丁、扩缩容、盯监控。

这种情况下，你真的还想去伺候 EC2 实例？去操心 Kubernetes 集群升级？去半夜处理某个节点磁盘爆了？

无服务器架构对一人公司的核心价值，不是「省钱」（虽然它确实省钱），而是「省心」。它把运维的心智负担从你肩上卸掉，让你把有限的精力花在真正该花的地方：产品和用户。

具体来说，无服务器给一人公司带来三个无可替代的优势：

第一，零运维开销。 不用打补丁，不用升系统，不用规划容量。Lambda 函数跑完拍拍屁股就走，你只为实际算力付费。对于请求量忽高忽低的早期产品来说，这种弹性简直是续命神器。

第二，天然按需付费。 你的服务可能一天才被调用几百次，传统架构下你也得养着至少一台实例 7x24 小时空转。而无服务器架构下，没请求就不花钱。对于还在摸索 PMF（产品市场匹配）的阶段，这意味着你可以同时跑好几个实验性服务，账单看了也不心疼。

第三，对 AI 极度友好的调试闭环。 这一点尤其关键。无服务器架构天然产出大量结构化日志，而这些日志恰恰是 AI 编程助手最能吃透的信息。当你用 AI 驱动开发时，它可以直接翻 CloudWatch 日志，读懂错误上下文，修 bug，重新部署，整个闭环几分钟就能跑通。传统架构很难做到这么丝滑。

但无服务器也不是银弹。冷启动延迟、供应商锁定、有限的执行时间，这些都是实打实的限制。关键在于：对一人公司的场景，这些限制基本都能忍，而它带来的好处却是决定性的。

二、为什么要自己造轮子

市面上已经有 Serverless Framework、SST、SAM 这些成熟方案了，为啥还要自己造轮子？

好问题。让我从第一性原理拆解一下。

先说语言选择。 我选 Rust 做后端，理由很朴素：Lambda 按执行时间乘以内存收费。Rust 编译出来的二进制体积小、启动快、内存省、跑得猛，这直接体现在更低的 Lambda 账单上。同样功能的 API，Rust 的运行成本可能只有 Node.js 的五分之一甚至十分之一。当你追求极致省钱的时候，语言选择本身就是架构决策。

但 Rust 在无服务器领域的生态远不如 Node.js 和 Python 丰富。没有哪个框架能给你从路由到数据库操作到认证到部署的一条龙体验。你要么自己东拼西凑一堆库，要么……

再说框架贴合度以及跟基础设施的适配度。 通用框架为了兼容各种场景和服务商，不得不堆上一层又一层的抽象。然而，无服务和基础设施天然是深度耦合的，过度的抽象和通用化，使得框架无法将特定基础设施的特性发挥到极致。如果我想极致地使用 SSM / CloudFront / KVS / SQS / EventBridge 等 AWS 服务，我还是需要自己写大量的胶水代码，通用框架的价值大大缩水。

最后是 AI 的 buff 加成，这才是真正的降维打击。 2026 年造一个框架的成本，和两年前完全不是一回事。我用 Claude Code 作为核心开发工具，写一份详细的设计文档，直接在终端里让它去实现。整个框架核心代码，从设计到落地也就半天。

这里有个很多人没意识到的点：Rust + AI 是一对天生的黄金搭档。Rust 的类型系统和编译器就像一位严厉的师父，AI 写出来的代码只要能过编译，质量下限就有保证。换成 Python 或 JavaScript，AI 生成的代码跑起来可能「看上去没问题」，但暗藏各种运行时 bug，而 Rust 的编译器会在代码落地之前就把这些坑拦住。类型即文档，编译即测试，这种「先验式」的质量保障让 AI 的产出可信度大幅提升。

当造轮子的成本足够低时，「自己造」就不再是奢侈品，而是理性选择。

三、架构全景：一个 Lambda 统治一切

先来看看整体架构，然后我们逐个拆解设计决策。

核心设计理念就是 一个 Lambda 打天下。所有 HTTP 路由都塞进同一个 Lambda 函数，内部用 axum 的 Router 做分发。听起来是不是有点反直觉？不是应该一个端点一个函数吗？

不，恰恰相反。

单函数模型有三个好处： 第一，冷启动的「品种」只有一个。十个端点分十个函数部署，每个函数都有各自的冷启动概率。合并成一个之后，热度集中，冷启动频率直线下降。第二，部署贼简单，就一个二进制文件，完事儿。第三，所有路由共享连接池、配置缓存等资源，不浪费。

框架（我管它叫 operon）用 workspace 结构组织，按职责拆成多个 crate：

fn router() -> Router {
    Router::new()
        .route("/health", get(|| async { "ok" }))
        .route("/users", get(list_users).post(create_user))
        .route("/users/{id}", get(get_user))
        .layer(
            OLayer::new()
                .request_id()    // 请求追踪 ID
                .tracing()       // 结构化日志
                .cors(CorsConfig::permissive())
                .error_format()  // 统一 JSON 错误格式
        )
}

async fn list_users(
    State(state): State<AppState>,
    JwtAuth(claims): JwtAuth<Claims>,  // 自动验证 JWT
    Query(params): Query<ListParams>,
) -> Result<Json<Vec<User>>, AppError> {
    let db = DynamoClient::new(&state.aws_config);
    let users = db.query("users")
        .key_condition("pk = :pk")
        .expression_value(":pk", "USERS")
        .limit(params.limit.unwrap_or(20))
        .send()
        .await?;
    Ok(Json(users))
}

几十行代码，一个带认证、带日志、带 CORS、带结构化错误处理的生产级 API 就齐活了。这就是框架要做到的效果。

说句实话，这套 API 设计之所以能做到如此简洁，离不开和 Claude Code 反复打磨的过程。我先写了一版「理想中的用户代码」长什么样，然后让 Claude Code 倒推框架内部需要怎样的抽象才能撑起这种简洁性。这种「从外向内」的设计方法，在 AI 辅助开发中效率奇高，因为 AI 最擅长的就是「给定约束条件，找到满足约束的实现」。一个人坐在那里空想 API 设计，可能琢磨三天还拿不准；扔给 Claude Code 一个目标形态，十分钟就能给你三套备选方案，附带优劣分析。

四、关键设计决策

4.1 混合配置策略：环境变量 + SSM 参数存储

一个看着简单、实际上极其重要的决策：配置和密钥怎么管？

很多框架把所有配置一股脑塞进环境变量。问题是，环境变量在 Lambda 控制台上裸奔，在 CloudFormation 模板里也是明文。你的 JWT 签名密钥、API 密钥、Webhook 密钥，这些敏感信息不该出现在任何明文配置中。

我的方案是打组合拳：

非敏感配置（项目名、环境标识、表名前缀等）走环境变量注入，这些值由 IaC 工具在部署时设好，读取快、控制台一眼能看到，方便排查问题。

敏感配置（JWT 密钥、API 密钥等）存在 SSM 参数存储里，用 KMS 加密。Lambda 函数冷启动时一次批量 GetParametersByPath 调用把所有密钥拉下来，缓存在内存里。后续的热请求直接走缓存，零开销。

这个设计妙在哪？第一，密钥永远不会出现在 Lambda 配置中。第二，冷启动时只需要一次 SSM API 调用，而不是每个密钥单独请求一次。第三，密钥轮换只要更新 SSM 参数就行，下次冷启动自动生效，不用重新部署。

4.2 去除 API Gateway：每百万请求省一美元

这是 operon 中 ROI 最高的一刀。

一般在使用 lambda 函数时，aws 推荐配对使用 API Gateway (v2)。API Gateway 可以做路由分发，可以限速，可以（做有限的）安全认证。但很多时候，我们也就拿 API Gateway 中转请求。

在开始的设计中，我的用法正是如此：一个 $default 路由，所有请求无脑代理到同一个 Lambda 函数。没用授权器（认证在 Lambda 里做），没用请求验证（在 axum 中间件里做），没用速率限制（暂时不需要）。

说白了，API Gateway 在我的架构里就是个每百万请求收一美元的透传管道。

Lambda Function URL 提供了完全一样的能力（接收 HTTP 请求、触发 Lambda），但它零费用（Lambda 调用费本来就要付的）。

月请求量API Gateway 费用Function URL 费用月节省
100 万$1.00$0.00$1.00
1000 万$10.00$0.00$10.00
1 亿$100.00$0.00$100.00

但 Function URL 有个硬伤：不支持自定义域名。解法是前面套一层 CloudFront。CloudFront 的费用大约 $0.10/百万请求（按 1KB 平均响应算），还是比 API Gateway 便宜 90%。

更妙的是，全栈应用（前端 + API）本来就要用 CloudFront 托管前端静态资源。把 API 也走 CloudFront 路由，相当于零增量成本。

安全这边也不用操心：Function URL 配置为 AWS_IAM 认证类型，公网直接访问不了。CloudFront 通过 OAC（Origin Access Control） 对每个请求做 SigV4 签名，只有经 CloudFront 转发的请求才能到达 Lambda。说实话，这比裸奔的 API Gateway 端点还安全。

使用 OAC 的代价是 Authorization header 被占用，如果你的应用也需要使用这个 header，可以换成诸如 X-Authorization。如果你不喜欢这个，也可以使用公网可访问的 Function URL + CF/Lambda 之间共享的 API key。

4.3 认证体系：从 JWT 到 OIDC

认证是每个 API 服务绑不开的话题。operon 在这块提供了三层能力：

第一层：JWT 验证（无状态）。 最常见的场景。通过 axum 提取器（extractor）实现，支持 EdDSA（Ed25519）、RS256、ES256 三种算法，默认推荐 EdDSA：密钥更短，签名更快，安全性更高。JWKS（JSON Web Key Set）可以丢在 S3 + CloudFront 上托管，几乎不花钱。

第二层：API Key 验证。 给服务间调用用的。通过 X-API-Key 头传递，用常量时间比较（constant-time comparison）防时序攻击。密钥存在 SSM 参数存储里。

第三层：OIDC 登录流程。 当你的应用需要接入 Google、GitHub 等第三方登录时，框架提供了完整的服务端 Authorization Code + PKCE 流程。临时状态用 AES-256-GCM 加密塞进 cookie，不需要任何服务端存储（比如 Redis）。流程走完后，框架签发自己的 JWT，后续请求走第一层的无状态验证。

为什么要在框架层面搞 OIDC？因为 OIDC 流程牵扯密码学（PKCE、签名验证、加密 cookie）、安全最佳实践（CSRF 防护、nonce 验证、时序攻击防护）和复杂的状态管理。每个项目都自己写一遍，翻车概率极高。框架化之后，写几行配置就能拥有生产级的登录能力：

顺便说一句，OIDC 这块是 Claude Code 发挥最大价值的地方之一。OIDC 流程涉及 PKCE 生成、state 加密、nonce 验证、ID Token 签名校验等大量密码学操作，手写极其容易出错。我把 OIDC 规范和安全最佳实践整理成设计文档，Claude Code 据此生成了完整的实现，包括边界情况处理和时序攻击防护。然后我逐行审查关键的密码学路径，确保没有安全隐患。这种「AI 出活，人审安全」的协作模式，特别适合一人公司：你不用成为密码学专家，但你需要有足够的判断力来守住安全底线。

4.4 DynamoDB 封装：够用就好

DynamoDB 封装的哲学是薄包装，不做 ORM。AWS SDK 的 DynamoDB 客户端 API 又臭又长，每个操作都要写一堆样板代码。框架做的事很简单：

  • 自动处理表名前缀（dev 和 prod 环境隔离）
  • 自动用 serde-dynamo 做序列化 / 反序列化
  • 统一错误映射（DynamoDB 的 ResourceNotFoundException 自动变成 HTTP 404）
  • 批量操作自动重试 UnprocessedKeys/UnprocessedItems

但它不碰 ORM 的活儿：没有查询 DSL，没有关系映射，没有迁移工具。如果你需要复杂的 DynamoDB 操作，直接用 SDK 就好。框架只负责让 80% 的日常操作写起来舒服。

4.5 Webhook 验证：可插拔架构

接收第三方回调（比如支付通知、代码提交通知）这种场景，框架提供了一套基于 trait 的验证体系：

#[async_trait]
pub trait WebhookVerifier: Send + Sync + 'static {
    type Event: DeserializeOwned + Send;
    async fn verify(
        &self, headers: &HeaderMap, body: &Bytes

operon 内置了 Stripe、GitHub 和通用 HMAC 三种验证器。你也可以给任何第三方写自己的验证器。关键在于：验证器作为 axum 中间件运行，在请求体到达业务处理器之前就把签名验了。业务代码拿到的一定是验证过的数据，从根上杜绝「忘了验签名」这种安全隐患。

cli deploy 背后的流程值得展开聊聊，几个关键设计决策：

ARM64 优先。 Lambda 的 ARM64（Graviton）实例比 x86_64 便宜约 20%，而 Rust 的 ARM64 交叉编译已经非常成熟。默认走 ARM64，属于白捡的成本优化。

Pulumi 而非 Terraform。 IaC 工具选了 Pulumi（TypeScript），因为编程模型更灵活，状态管理可以用 S3 后端，而且 AI 生成 TypeScript 代码的能力吊打生成 HCL 配置。使用代码还有一个好处是你可以极致地封装，重构，打包，层次化设计，而这些都是非代码的配置系统无法达到的。

部署前强制预览。 生产环境部署时，CLI 会先跑一遍 pulumi preview 展示变更摘要，然后要求人工确认。这个小小的「减速带」，在你一个人操作、没有队友帮你 double-check 的情况下尤为重要。CI/CD 场景下可以用 --yes 跳过。

全局配置与项目配置分离。 AWS 账号 ID、Pulumi 后端地址、证书 ARN、Route53 Zone ID，这些「基础设施关注点」从项目配置里剥离出来，统一塞进全局的配置。项目配置只管业务：Lambda 内存给多大、要哪些 DynamoDB 表、前端怎么构建。这样新项目的配置文件可以短到只有二十行。

六、基础设施抽象：从 600 行模板到 80 行配置

随着 operon 迭代，基础设施代码的模版越来越大，生成的文件越来越难以阅读。我做了一个更进一步的优化：把 Pulumi 基础设施代码抽成一个可复用的 npm 包。

之前的做法是： CLI 用模板引擎生成一个大约 600 行的 TypeScript 文件，里面塞满了所有 Pulumi 资源定义：Lambda、CloudFront、DynamoDB、S3、IAM、Route53… 条件分支盘根错节，还内嵌了 55 行 CloudFront Function 的 JavaScript 代码。这个模板是整个代码库里最让人头大的部分。

现在的做法是： 把这些资源定义封装进一个带类型的 TypeScript npm 包，发布到私有包注册表。项目里的 infra/index.ts 变成了纯配置：

你也许会问，为何一开始不这么做？这是因为抽象是有成本的，operon 在没有「用户应用」之前，方向是不明朗的，而且由于我们还没有 npm 私有包支持。后来做 crate/npm 私有包无服务系统 chromatin 时，作为第一个用户应用，operon 的方向在 chromatin 的构建中渐渐明确，当 chromatin 部署成功后，我们就有了抽象 operon 基础设施代码并将其发布到 chromatin 的能力，然后发布后，反过来 chromatin 的部署代码也得到了大大的简化。这种螺旋式的互相成就互相进步的 bootstrap 故事，在整个开发过程中非常常见。

回归正题。80 行配置，零基础设施逻辑。 IAM 策略、CloudFront 行为、OAC 安全模型、SPA 路由处理，全部封装在 npm 包内部，经过测试，版本化发布。

这个转变还有一个附带好处：基础设施更新和 CLI 发布彻底解耦。 要调整 IAM 策略或 CloudFront 缓存配置？发个新版本的 npm 包，项目跑一下 npm update 再 operon deploy 部署就行，不用重新编译 Rust CLI。

七、代码质量工程：让框架更难被误用

大量用 Claude Code 生成代码之后，我发现一个规律：API 越坑，AI 越容易翻车。一个函数接受七个位置参数，AI 迟早把顺序搞混。一个模块的内部实现暴露为公开 API，AI 就会依赖这些本不该依赖的细节。

这不是 AI 的问题，是 API 设计的问题。好的 API 设计，本质上就是「让正确的用法成为最自然的用法」，对人如此，对 AI 亦然。当你用 Claude Code 开发时，它就是你最频繁的 API 消费者。为 AI 设计友好的 API，等于为所有使用者设计友好的 API。

所以，框架在 API 设计上做了大量「防呆」工作：

Builder 模式干掉多参数构造函数。 框架的核心配置结构体用 typed-builder，每个字段都通过具名方法设置，从根上杜绝参数位置搞混：

AppConfig::builder()
    .project("test".into())
    .environment("dev".into())
    .region("us-east-1".into())
    .secrets(secrets)

严格的可见性管控。 内部实现模块一律 pub(crate)，只暴露用户真正要用的公开 API。API 表面积小了，AI 误用内部接口的概率也就低了。

语义级配置校验。 配置文件里的约束值（比如 Lambda 架构类型、DynamoDB 计费模式）用枚举类型而非字符串，反序列化的时候就能逮住错误，不用等部署时才傻眼：

宏消灭重复代码。 DynamoDB 的各种操作构建器（query、scan、update、get、delete）共享大量相同的方法签名（expression_name、expression_value、key）。这些方法用声明式宏统一生成，行为一致，维护成本也降下来了。

八、成本实测：一杯咖啡撑一个月

来算一笔账。假设你的服务还在早期阶段，月请求量大约 50 万次：

服务月费用
Lambda（256MB ARM64，平均 50ms）~$0.10
DynamoDB（按需模式，100 万读/写）~$1.25
CloudFront（50 万请求 + 1GB 传输）~$0.10
S3（静态资源 + 日志）~$0.05
CloudWatch 日志（30 天保留）~$0.50
SSM 参数存储（标准参数免费）$0.00
Route53 托管域名$0.50
总计~$2.50

两块五美金一个月。真的连一杯咖啡都不到。

当然，随着流量涨起来，费用也会涨。但 DynamoDB 的按需模式和 Lambda 的按量计费保证了成本和流量线性挂钩，不会出现「流量涨了 10% 账单涨了 200%」的离谱跳变。

九、AI 驱动开发的闭环

最后聊聊这个框架是怎么造出来的。这个过程本身就是「一人公司」工作方式的缩影，也是我一直强调的编程的未来：AI + Rust + SDD。

9.1 工具：Claude Code

整个框架的开发，我的主力工具是 Claude Code。一个典型的开发场景是这样的：我给定目标和约束，和 Claude Code 一起讨论出来一个设计文档，然后在设计文档上反复迭代，达到一个不错的状态，然后把文档喂给 Claude Code，让它按这个设计实现。它开始写代码，写完后 build/lint/fmt/test 都通过后，调用 codex review 技能，仔细 review 代码，然后它确认需要修改的问题后整改，然后再 build/lint/fmt/test。如果容易手工验证（如 API/web），就让 Claude Code 手工验证，直至一切 ok，然后提交 PR。

整个过程我就在旁边悠哉喝着咖啡跟另一个 Claude Code 讨论另一个项目的下一步。当 PR 提交后，我才会上手审查关键逻辑。

这就是 Rust + AI 的魔法所在：编译器充当了一个永不疲倦的 Code Reviewer。AI 写出来的代码如果有内存安全问题、类型不匹配、生命周期错误，编译器当场拦截。Claude Code 读得懂 rustc 的错误信息，也可以找到 lambda fn 的相关日志，找到问题所在，然后自己修正。这种「AI 写码，编译器兜底，看日志修 bug」的模式，让 AI 产出的代码有足够的质量（当然日后需要定期让它自我修复技术债）。

9.2 规格驱动开发

整个框架的核心设计文档从最开始的一份，逐渐演进成多份，覆盖了框架架构、认证系统、API Gateway 迁移、代码加固、全局配置和基础设施 npm 包。每份文档的产出流程都是：先和 Claude Code 对需求，让它出初稿，我审阅修改，来回几轮后定稿。

定稿后的设计文档就变成了 Claude Code 的「施工图纸」。每个文档末尾都列了明确的实现步骤，Claude Code 按顺序逐步推进，每完成一个阶段就跑构建、测试、lint，通过了再往下走。

规格驱动开发（Spec-Driven Development）在这个项目中得到了充分验证。设计文档不是走过场，它们是 AI 能正确干活的前提。 没有清晰的设计文档，AI 写出的代码会在方向和风格上反复横跳；有了设计文档，它就能像一个靠谱的工程师一样稳定交付。

9.3 迭代速度：从天到小时

当我决定把 API Gateway 干掉，迁移到 Function URL + CloudFront 的架构时，这涉及到基础设施模板改写、OAC 安全配置、CloudFront Function 的 URL 重写逻辑、以及运行时的兼容性验证。如果纯手工，光查文档就要花大半天，改完再调试少说两三天。

实际操作是这样的：我把迁移方案写成设计文档（半小时），喂给 Claude Code（一分钟），它输出了完整的 Pulumi 基础设施代码变更和 CloudFront Function 代码（二十分钟），部署到 staging 修改错误直到验证通过（十分钟）。从决策到上线，总共才一小时。

再比如 OIDC 模块。完整的 Authorization Code + PKCE 流程，包括加密 cookie 状态管理、ID Token 验证、JWT 签发，Claude Code 在半个小时就交付了初版。我立刻让 Claude Code 将其应用在其他项目，验证、修改、再验证，很快就合入主线了。传统开发节奏下，这至少是两周的工作量。

9.4 一人公司的新可能

整个框架从设计到落地，大约花了半天时间。纯人工开发的话，保守估计得一个月。Claude Code 带来的提效大约在 10 倍以上，这还没算上设计文档本身也是 AI 协助撰写的效率加成。

但比效率提升更重要的是一个质变：AI 让「一人公司自建框架」从不可能变成了可能。 以前，自建框架是大厂才玩得起的奢侈品，你需要一个团队花几个月来设计、实现、测试、文档化。现在，一个人加一个 AI，就能产出质量不输团队作品的定制框架。

这不是在夸张。整个框架的代码，包括类型安全的 Builder API、完整的错误处理链路、生产级的 OIDC 实现、从 CLI 到基础设施的全链路自动化，这些都是一个人在 Claude Code 的加持下完成的。在此基础上，我用它做了 Rust crate/npm 的私有包仓库软件 chromatin，并构建了一开始我想做的产品 AI slides，整个过程非常丝滑，三四个系统并行开发，螺旋进化。工具变了，生产力的上限就变了。

十、经验总结与建议

回顾整个项目，如果你也在给一人公司搭基础设施，以下几条经验或许有用：

第一，无服务器不是银弹，但对一人公司来说是最优默认解。 它消除了你最扛不住的东西：运维负担。在你真正需要长连接、WebSocket 或超长计算任务之前，别急着引入容器或虚拟机。

第二，成本优化的 80% 来自架构决策，不是代码调优。 选 Rust 而非 Node.js、选 ARM64 而非 x86_64、干掉 API Gateway，这些决策带来的降本效果，远不是代码层面省几毫秒执行时间能比的。

第三，自建框架的窗口期到了，抓住它。 Claude Code 这样的 AI 工具把框架开发的成本拉低了一个数量级。通用框架不合脚？与其花时间绕过它的各种限制，不如花同样的时间按自己的需求量身打造一个。短时间的投入，换来的是未来每个项目都能省下的时间和账单。

第四，选 Rust，让编译器替你看住 AI。 如果你的 AI 助手要帮你写大量代码，那代码的质量保障就至关重要。Rust 的类型系统和所有权模型就是天然的安全网，AI 生成的代码只要编译通过，内存安全、线程安全、类型正确性都有保证。这种「编译即验证」的特性，让 Rust 成为 AI 编程时代最值得投资的语言之一。

第五，设计文档是 AI 时代最重要的「代码」。 写一份好的设计文档，可能比写十个代码文件还值钱。它决定了 AI 产出的上限。和 Claude Code 协作的核心节奏是：你负责想清楚（写设计文档），它负责做出来（写实现代码）。想不清楚就动手，AI 只会帮你更快地走向错误的方向。

第六，别追求完美，够用就行。 我的 DynamoDB 封装不是 ORM，我的 S3 封装不是文件系统，我的 Webhook 验证只支持三个提供商。但它们覆盖了 95% 的使用场景。剩下那 5%，有了 AI，需要的时候再补也是分分钟的事。

善弈者通盘无妙手。一人公司的基础设施也是如此：没有惊天动地的技术，但每一步都精打细算、环环相扣。
